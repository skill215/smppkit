# Independent submit_multi wire samples

These synthetic frames were authored from the ordered fields in SMPP 3.3
§6.3.4, 3.4 §4.5 and 5.0 §4.2.3. They are literal test inputs and expected
outputs, not dumps generated by smppkit. Both fit all three profiles and contain
no TLVs. Hex whitespace separates fields and is not part of the frame.

## Request: SME plus distribution list

```text
00000035 00000021 00000000 01020304
434d5400
050073726300
02
01 0101 31323300
02 67726f757000
00 00 01 00 00 01 00 03 00 02
6869
```

| Offset | Bytes / meaning |
| ---: | --- |
| 0 | 53-byte total frame; command 0x21; status 0; sequence 0x01020304 |
| 16 | Service `CMT` followed by NUL |
| 20 | Source TON 5, NPI 0, address `src` followed by NUL |
| 26 | Two destinations |
| 27 | SME flag 1, TON 1, NPI 1, address `123` followed by NUL |
| 34 | List flag 2, name `group` followed by NUL |
| 41 | ESM class 0, protocol 0, priority 1 |
| 44 | Empty schedule and validity (one NUL each) |
| 46 | Registered delivery 1, replacement 0, DCS 3, default message ID 0 |
| 50 | Payload length 2; bytes `68 69` (`hi`) |

## Response: OK header with one failed SME

```text
00000020 80000021 00000000 01020304
69643a3700
01
0101 31323300 00000058
```

The 32-byte response carries opaque ID `id:7`, one unsuccessful SME (`123`,
TON/NPI 1/1), and 32-bit status 0x00000058 (throttled). Header status 0 must not
hide that failure. The distribution list's members cannot be inferred from
this exchange. Neither header status nor absence from this list proves handset
delivery, and the library does not retry the failed or uncertain destinations.

[`codec/multi_test.go`](../codec/multi_test.go) checks both encoding against
these bytes and decoding them into explicit expected structures, plus every
truncated body prefix. [`session_multi_test.go`](../session_multi_test.go)
uses an independent peer with sequence 1 and individual status 0x12345678 to
verify all four status octets survive. That peer compares the complete request
and writes the literal response one byte at a time without using Codec.

Standard-TLV samples are in [`codec/tlv_standard_test.go`](../codec/tlv_standard_test.go).
For example, `0428 0001 50` is 5.0 congestion_state 80, and
`0381 0004 01010131 0302 0001 08 0303 0002 0041` combines a callback number
with presentation and alpha-tag values. Tests supply independently specified
mandatory bodies and compare complete frames for every listed standard tag;
they also check malformed values, version/command restrictions and dependencies.

## Scheduled submission and versioned delivery fields

The following 76-byte frame is an independently authored submit_sm sample for
3.4/5.0. It uses source `src` (TON 5/NPI 0), destination `123` (1/1), service
`CMT`, mode 3, priority 3, absolute schedule `240229235959948+` and relative
validity `000001000000000R`. The schedule is a leap day at the maximum UTC
quarter-hour offset; validity is a one-day offset. These are fixed synthetic
wire values, not a recommendation to submit a past schedule to a live SMSC.

```text
0000004c 00000004 00000000 00000007
434d5400 050073726300 010131323300
03 00 03
3234303232393233353935393934382b00
3030303030313030303030303030305200
1e 01 08 00 02 0041
```

The field offsets, including the 16-byte header, are:

| Offset | Field |
| ---: | --- |
| 16 | Service type (4 bytes) |
| 20 | Source TON/NPI/address (6 bytes) |
| 26 | Destination TON/NPI/address (6 bytes) |
| 32, 33, 34 | ESM class, protocol ID, priority |
| 35 | Schedule (17 bytes) |
| 52 | Validity (17 bytes) |
| 69..73 | Registered delivery, replacement, DCS, default ID, length |
| 74 | Two payload bytes `00 41` |

Registered delivery 0x1e requests failure receipts, SME acknowledgements and
intermediate notifications. The binary payload uses DCS 8. Changing command
ID to 0x00000005 produces valid 5.0 deliver_sm forwarding fields; 3.4 rejects
those nonempty fields. 3.3 rejects this sample's relative time and newer flag
values. Separate tests confirm 3.3 accepts its absolute delivery fields.

## Query final dates

All three profiles accept this 39-byte response with opaque ID `m:7`, final
date `241231235959000-`, state 2 and zero error code:

```text
00000027 80000003 00000000 00000007
6d3a3700 3234313233313233353935393030302d00 02 00
```

The older local response-date form is accepted in 3.3/3.4 and rejected in 5.0:

```text
00000023 80000003 00000000 00000007
6d3a3700 32343132333132333539353900 02 00
```

These fixtures and boundary mutations live in
[`codec/semantics_test.go`](../codec/semantics_test.go). Tests also construct
malformed frames directly, including reserved flags and impossible dates,
since the normal encoder must reject those bodies. See the
[time interpretation decisions](field-semantics.md#time-grammar-and-recorded-interpretations).

## data_sm request and response direction

These three frames are transcribed independently in
[`codec/data_direction_test.go`](../codec/data_direction_test.go). Ordinary
3.4/5.0 Codec decoding accepts them; contextual validation supplies the original
request direction. They are synthetic fixtures, not captured customer traffic.

Delivery receipt, 38 bytes, sequence 7:

```text
00000026 00000103 00000000 00000007
00 000000 000000 04 00 00
001e 0003 696400
0427 0001 02
```

| Offset | Field |
| ---: | --- |
| 16 | Empty service type |
| 17..19 | Source TON/NPI zero and empty address |
| 20..22 | Destination TON/NPI zero and empty address |
| 23..25 | esm_class 4, registered_delivery 0, data_coding 0 |
| 26..32 | receipted_message_id TLV, `id` plus NUL |
| 33..37 | message_state TLV, value 2 |

Both versions accept this in delivery context and reject it in submission
context. 5.0 allows ESM type 4 on submission, but its receipt TLVs are still
delivery-only. An empty address is wire-valid and does not imply carrier
acceptance or successful receipt correlation.

TTL-bearing request, 34 bytes, sequence 7:

```text
00000022 00000103 00000000 00000007
00 000000 000000 02 00 00
0017 0004 0000003c
```

Mandatory offsets are the same; esm_class is 2 (transaction mode on submission).
The TLV at offset 26 is qos_time_to_live, value 60 seconds. Submission accepts
this in 3.4/5.0. Delivery accepts it in 3.4 (including the ignored low mode bits)
but rejects it in 5.0, whose delivery optional-parameter table excludes TTL.

Response, 23 bytes, sequence 7:

```text
00000017 80000103 00000000 00000007
6d00
0420 0001 01
```

Offset 16 contains message ID `m` and its terminator; the dpf_result TLV starts
at offset 18 and reports value 1. Both versions allow it as a submission
response (MC to ESME) and reject it as a delivery response (ESME to MC).
The ordinary Codec does not infer which request preceded it. This illustrates
direction applicability, not a guarantee about the original request's outcome;
transaction-mode-specific response policy remains outside this check.

[`session_data_test.go`](../session_data_test.go) also uses a peer without Codec
to check a full 26-byte request and fragment a literal DPF response one octet
at a time. Separate independent requests place receipt state on submission and
set_dpf on delivery to verify rejection before inbound admission.

## data_sm transaction request and failure response

Independent fixtures in
[`codec/data_response_test.go`](../codec/data_response_test.go) describe an
explicit transaction submission, 26 bytes, sequence 7:

```text
0000001a 00000103 00000000 00000007
00 000000 000000 02 00 00
```

Offset 23 is esm_class 2, selecting transaction mode. Registered delivery and
data coding at offsets 24/25 are zero. Changing offsets 23/24 to `01 01` makes
an invalid datagram submission: the directionless Codec still decodes it, but
submission-context validation rejects its receipt request. Delivery context
does not infer an original submission mode from these bits.

The failure response is 35 bytes:

```text
00000023 80000103 000000fe 00000007
6d00
0425 0001 00
0423 0003 030001
0420 0001 01
```

| Offset | Field |
| ---: | --- |
| 8..11 | command_status 0xfe, delivery failure |
| 16..17 | Opaque ID `m` plus NUL |
| 18..22 | delivery_failure_reason 0, destination unavailable |
| 23..29 | network_error_code, GSM type 3 and opaque error 0x0001 |
| 30..34 | dpf_result 1 |

Both profiles accept this response for an explicit transaction submission and
reject it for explicit datagram/store-and-forward submission. Default mode zero
remains unresolved and is preserved. Changing the response's status to OK
creates a contradiction with failure_reason for explicit transaction mode;
ordinary decoding still succeeds, but ValidateDataResponse rejects it.

This 25-byte diagnostic response illustrates the version distinction:

```text
00000019 80000103 00000008 00000007
6d00 001d 0003 6f6b00
```

The text TLV at offset 18 is `ok` plus NUL; text contents do not override status
8. For an explicit datagram submission, 3.4 accepts this diagnostic and 5.0
rejects it under its transaction-only submission-response table. The associated
raw-peer tests use sequence 1 and send each response octet separately. These
examples establish field applicability, not external carrier interoperability.

## One-way alert and outbind

[`codec/notification_test.go`](../codec/notification_test.go) compares typed
bodies with these independently specified frames in both 3.4 and 5.0; 3.3
rejects both. Neither command has a response command.

Availability notification, 33 bytes, sequence 7:

```text
00000021 00000102 00000000 00000007
01 01 31323300
05 00 61707000
0422 0001 00
```

Source TON/NPI at offsets 16/17 are 1/1; address `123` starts at offset 18.
ESME TON/NPI at offsets 22/23 are 5/0; `app` starts at offset 24. The TLV at
offset 28 is ms_availability_status, value 0 (available). Session accepts this
only from an MC on an RX/TRX bind, and emits no ACK. An independent peer checks
that the next outgoing bytes are the application's enquire_link instead.

Outbind, 22 bytes, sequence 7:

```text
00000016 0000000b 00000000 00000007
6d6300 707700
```

The synthetic system ID `mc` starts at offset 16; password `pw` starts at 19.
These are demo credentials, not captured traffic. Outbind carries no version
byte and no TLVs. Standalone Codec validates layout independently of Session
state; the ESME Session admits it only before binding and only once.

`server_outbind_test.go` uses an independent ESME to inspect the same outbind
body with MC sequence 1, then sends this 5.0 receiver bind using ESME sequence 9:

```text
0000001d 00000001 00000000 00000009
65736d6500 707700 00 50 00 00 00
```

The 24-byte bind response is:

```text
00000018 80000001 00000000 00000009
6d6300 0210 0001 50
```

The 3.4 variant changes only the interface-version octets to 34. The next MC
notification uses sequence 2, so a late Generic NACK referring to outbind's
sequence 1 cannot complete new work. These bind frames are independent protocol
operations, not an invented outbind_resp. See the [endpoint contract](notifications.md).

## Crossed unbind and independent TCP lifecycle peer

`session_lifecycle_test.go` uses these four independent 16-byte frames. The
requests use separate direction-local sequences; their responses echo them.

```text
00000010 00000006 00000000 00000001
00000010 00000006 00000000 00000009
00000010 80000006 00000000 00000009
00000010 80000006 00000000 00000001
```

The last two frames may complete in either order. Closing after only one loses
an outstanding obligation. Each field is four octets: length at 0, command at 4,
status at 8 and sequence at 12. There is no body or TLV in these samples.

`session_interoperability_test.go` builds headers directly from protocol integers
and these literal bodies. Its client submit is 35 bytes, sequence 2, payload `hi`:

```text
00000023 00000004 00000000 00000002
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 02 6869
```

All mandatory strings are empty; the sixteen zero octets encode the empty
service/address/time strings and fixed scalar fields. sm_length at offset 32 is
2; payload starts at 33. This minimal address case tests framing, not SMSC routing.
The peer accepts it with opaque message ID `s1`:

```text
00000013 80000004 00000000 00000002 733100
```

After query sequence 3 times out, the peer coalesces these four frames in one
write. The late query response has message ID `s1`, empty final_date, state 1 and
error_code 0. Only the live enquire response completes the current request;
the final inbound enquire has its own response obligation despite sequence 4:

```text
00000016 80000003 00000000 00000003 733100000100
00000013 80000004 00000000 00000002 733100
00000010 80000015 00000000 00000004
00000010 00000015 00000000 00000004
```

These frames apply to all three profiles and carry no TLVs. The TCP test also
checks a TX bind whose interface byte is 33/34/50, followed by a 19-byte 3.3
response or 24-byte 3.4/5.0 response advertising sc_interface_version. Its closing
local unbind uses sequence 5 rather than 1. Frame seeds extend FuzzDecode;
coalesced input must be read as separate frames, never accepted as one Decode PDU.


## Release 1.0 R1 regression bytes

`session_r1_test.go` promotes the review probes into regular tests. A raw peer
performs an actual TX bind and sends literal responses; no shared Codec creates
these peer frames. The following 5.0 bind response contains system_id `mc` but
no `sc_interface_version` advertisement:

```text
00000013 80000002 00000000 00000001 6d6300
```

After that bind, this Codec-valid enquire response is rejected by Session's
negotiated policy; the request remains Written/uncertain, not ResponseReceived:

```text
00000015 80000015 00000000 00000002 0428 0001 01
```

With an explicit version advertisement, the same response is accepted:

```text
00000018 80000002 00000000 00000001 6d6300 0210 0001 50
```

Negative responses and NACKs do not bypass this policy. For example, a NACK with
status 8 and congestion_state is retained as a PeerError only when negotiated:

```text
00000015 80000000 00000008 00000002 0428 0001 01
```

The same tests cover 3.4/5.0 data_sm_resp with a customer TLV, enabled/disabled
negotiation, and TLV-free controls. `TestR1ResponseBeforeWriteCompletion` gates
Write after the raw peer has read the request and sent its response; fake time
then drives cancellation or deadlines, preserving exact response/byte counts.

`message/r1_test.go` retains the earlier literal 3.3 submit frame with DCS 3 and
payload `40` as a low-level Codec preservation case. The high-level built-in
Latin-1 planner now rejects that 3.3 policy, including after fallback. The wire
Codec still preserves raw DCS; interpreting an explicit peer mapping belongs to
the low-level caller. Later-version Latin-1 and supported 3.3 encodings retain
independently specified payload-byte assertions.

## RV20 append isolation and RV21 automatic ACK boundary

The formal tests in `codec/ownership_regression_test.go` include a data_sm with
two customer values (0x1500=`11`, 0x1501=`22`), valid in both 3.4 and 5.0:

```text
00000024 00000103 00000000 00000001
00000000000000000000 1500 0001 11 1501 0001 22
```

Appending five bytes to the first decoded value must leave the second at `22`.
The suite also covers zero-length values and short_message preceding a TLV,
through both Read and Decode; expected bytes do not come from Codec.Append.

`messaging_ack_regression_test.go` supplies explicit transaction submissions:

```text
# data_sm, 3.4/5.0, esm_class=02, message_payload="Hi"
00000020 00000103 00000000 00000001
00 000000 000000 02 00 00 0424 0002 4869

# submit_sm, 5.0, esm_class=02, short_message="Hi"
00000023 00000004 00000000 00000001
00 000000 000000 02 00 00 00 00 00 00 00 00 02 4869
```

AdmitMessage returns ErrState and retains no receiver state; it sends no response
and leaves the handle unclaimed. The test then explicitly rejects through
Respond, expecting the first peer-visible header/body below (data_sm example):

```text
00000010 80000103 00000008 00000001
```

RunReceiver instead returns ErrState and closes without ACK. Control samples
change mode/direction/version; delivery mode bits and the 3.3 delivery marker
remain outside the submission-mode rejection. Mode zero assumes the consuming
application chose a non-transaction default; the library cannot infer it.
## R2 high-level contract samples

`TestSendTextTransportOutcomes` uses this independent success response for the
first segment before injecting the second segment's transport failure:

```text
00000013 80000004 00000000 00000001 6f6b00
```

Length 19, submit_sm_resp, status OK, sequence 1, opaque ID `ok` plus NUL.
The injected cases write zero bytes, seven bytes or the entire second frame
without a response. Exactly two writes and a third NotAttempted result are
required; no production Codec constructs this response.

`TestAdmitMessageCrossSessionNamespace` composes empty-address submit_sm frames
with esm_class 0x40, sm_length 7 and literal user data:

```text
05 00 03 07 02 01 41
05 00 03 07 02 02 42
```

UDHL 5; 8-bit concatenation IE, reference 7, total 2, parts 1/2, payload A/B.
Each frame uses sequence 1 on a separate Session. The default namespace keeps
two incomplete groups; explicitly sharing a namespace completes `AB` once.
Existing protocol layout vectors remain the independent version-level evidence.
## R3 Generic NACK profile boundary

`TestIndependentGenericNACKProfiles` adds explicit literals across 3.3/3.4/5.0:

```text
00000010 80000000 00000008 00000000
00000010 80000000 00000008 7fffffff
```

Both are valid: nonzero status and sequence zero or the maximum allowed sequence.
The test rejects status zero, sequence `80000000` and a truncated header. This
congestion-bearing response is accepted only in 5.0; 3.3/3.4 NACK has no TLVs:

```text
00000015 80000000 00000008 00000001 0428000101
```

No production encoder constructs these expected bytes. Existing 3.4/5.0 NACK
Session and congestion checks remain in use; this closes direct 3.3 wire coverage.

## v1.1.0 automatic enquiry fixtures

The independent byte peer in `session_heartbeat_test.go` uses numeric wire
headers and authored bodies, never Codec.Encode/Decode. These control frames
apply unchanged to 3.3, 3.4 and 5.0; none contains TLVs:

```text
# enquire_link, sequence 1
00000010 00000015 00000000 00000001
# corresponding successful response
00000010 80000015 00000000 00000001
# unsuccessful response (system error)
00000010 80000015 00000008 00000001
# Generic NACK (invalid command ID), same pending sequence
00000010 80000000 00000003 00000001
# valid unbind_resp opcode, incompatible with the pending enquiry
00000010 80000006 00000000 00000001
```

The tests also send a successful response on an unrelated sequence, a duplicate
response, and an inbound enquiry reusing the outgoing probe's sequence. Only the
expected response in the outbound sequence space completes the probe. Virtual
time tests then check lifecycle/deadline policy without deriving expected bytes
from the implementation. Same-Codec examples are supplemental execution checks.

## v1.1.0 receipt fixtures

`message/receipt_test.go` contains complete synthetic literal PDUs. These expected
bytes are authored from field order, independently of BuildReceipt and Codec.
Sequence is 7, addresses are empty, and the opaque ID is `00Ab` (never parsed as
hexadecimal or converted to an integer).

3.4/5.0 deliver_sm with ASCII text `id:00Ab stat:DELIVRD` (20 bytes):

```text
00000035 00000005 00000000 00000007
00000000000000
04 00 00 00 00 00 00 01 00 14
69643a3030416220737461743a44454c49565244
```

The 3.3 fixture has the same bytes except DataCoding is 00, explicitly using the
legacy receipt-marker/unpacked-GSM convention. This particular text has the same
encoded bytes in both alphabets. Separate tests verify the GSM underscore byte
and malformed escape boundaries; 3.3 never acquires TLVs.

```text

00000000000000 20 00 00

```

