# v1.2.0: semantic diagnostics and binary segmentation

Created: 2026-10-29; updated: 2026-11-06 (Asia/Shanghai). **Release candidate, not published:
F1 stable semantic diagnostics and F2 binary helpers are implemented locally;
local overall review found no blocking code findings; release documentation
is finalized and candidate submission/CI verification is the current step.** Target the next minor version, v1.2.0, because
these are intended as compatible public API additions under the
[versioning policy](../compatibility.md#versioning).
No publication date is assigned. The binary API is documented below.

The [feature design](../v1.2.0-design.md), refined on 2026-11-06, specifies
priorities, APIs, compatibility contracts and implementation entry gates.
It retains the two-feature scope below. The [semantic catalog](../semantic-diagnostics.md)
and [binary DCS whitelist](../binary-dcs.md) are finalized. See the
[F1 validation record](../v1.2.0-f1-validation.md) and
[F2 validation record](../v1.2.0-f2-validation.md) for executed checks and limits.

The approved planning scope contains exactly two enhancements:

| Enhancement | v1.1.0 baseline | Planned outcome |
| --- | --- | --- |
| Stable semantic field/rule identifiers | DecodeError classifies failures; structural FieldError exists, but some semantic failures expose only a sentinel and diagnostic text | Inspect semantic field/rule identity without parsing Error() |
| High-level binary segmentation | Typed PDUs and Session.Request accept raw bytes; automatic preparation/sending is text-oriented | Prepare and send bounded binary multipart messages with the same outcome guarantees as SendText |

Keep Go 1.26, concrete PDU structs, the immutable versioned Codec and shared
Session. No required methods are added to existing extension interfaces.
Consumer migration can continue on v1.1.0; this roadmap does not declare a
new hard prerequisite for replacing another SMPP library.

## Stable semantic field and rule identifiers

Implemented locally as `codec.SemanticError` and `codec.SemanticRule` with
documented, stable field and rule identifiers in the semantic catalog.
Diagnostic prose remains non-contractual. Callers must tolerate future identifiers.

- Inventory built-in Codec semantic checks before freezing the identifier table.
  Cover encoding/preflight and decoding, including applicable public validation
  methods. Use protocol field names such as `source_addr_ton` and `data_coding`;
  separate rule identity from prose and from the offending value.
- Distinguish range/reserved-value, version, command/direction and cross-field
  constraints where the existing validator makes those distinctions. Define
  attribution for repeated fields and multi-field rules without inventing a
  byte offset when validation is performed on a typed PDU.
- Preserve errors.Is for existing causes, including ErrValidation and
  ErrUnsupported, wherever they currently apply. Preserve errors.As for
  structural FieldError and the existing DecodeError classification/context.
  A new semantic cause must not accidentally reclassify it as a structural error.
- Keep credentials, addresses, payloads and TLV values out of safe identifiers
  and error formatting. Do not interpret arbitrary extension-returned error text
  as a built-in field/rule, or discard extension causes.
- Retain first-error validation unless a separate change is justified. This
  does not add an aggregate validator, automatic NACK/status mapping, disconnect
  policy or retry policy.

Acceptance requires independent wire samples for invalid source TON and
data_coding, plus representative cross-field, version/direction and repeated
field cases. Compare equivalent typed-input and decoded-input diagnostics where
applicable. Verify cause identity, error classification, privacy and existing
structural diagnostics. Reuse existing valid-input fixtures to show that the
diagnostic addition does not change supported wire behavior. Benchmark valid
and invalid paths, recording B/op and allocs/op without equating them to copies.

## High-level binary preparation and sending

Implemented `message.PrepareBytes` and `Session.SendBinary`, using
`message.Binary` / `smpp.BinaryMessage` and `message.BinaryPolicy`. See the
[binary contract](../binary-messaging.md) for final fields, output accounting
and the explicit `Encoding="binary"` label.

- Accept owned/snapshotted raw `[]byte` and an explicit version-appropriate DCS.
  Preserve every payload octet, including NUL and invalid UTF-8. Do not route
  bytes through a text encoding, string surrogate, charset guess or fallback.
- The initial scope is binary/octet segmentation. Freeze a version-specific
  supported DCS table before implementation. Do not infer character boundaries
  for pre-encoded GSM/UCS-2 text or promise arbitrary-DCS splitting from bytes.
- Reuse the existing Plan preparation/materialization concepts, UDH builder,
  metadata validation and bounded reference leases. Preparation performs no I/O
  and reserves no reference; previews/materialized outputs have explicit owned
  storage. Reuse must preserve all existing text behavior.
- Provide explicit UDH8, UDH16, SAR and message_payload policies where the
  version and peer permit them. Account for concatenation headers, additional
  UDH/application ports, radio budgets, short_message and TLV length limits.
  Payload remains one SMPP request with any further segmentation owned by the
  peer, not a promise of one radio SMS or automatic library segmentation.
- Keep 3.3 TLV-free and preserve its current high-level submission limits: no
  implicit UDH multipart support where the selected 3.3 command contract lacks
  it. Do not weaken TLV negotiation or silently switch a requested mode.
- Reject conflicting caller/generated concatenation or payload metadata.
  Define allowed AdditionalUDH elements explicitly; this work adds no language
  table interpretation, packed-GSM handling or general EMS/WAP parser.
- Bound input bytes, segment count and output allocation before excessive work.
  Specify empty input, exact-fit and oversized-input behavior. Document owned
  buffers and limits rather than claiming zero-copy operation.
- Reuse Session's writer, window, correlation and cancellation, with client
  submit_sm and server deliver_sm paths following existing role/version rules.
  Preflight all segments before reserving a reference and writing any segment.
  Allow an application-owned References instance to span connections/reconnects.
- Reuse SendResult/SegmentResult where compatible; settle the Encoding label
  for raw bytes explicitly. Keep per-segment IDs, NotAttempted/NotWritten and
  uncertain outcomes. Stop scheduling on failure, retain all planned results,
  and do not retry automatically or release references on submission acceptance.
  Existing receive/reassembly and ACK policies remain unchanged.

Acceptance requires independent UDH8/UDH16/SAR/payload wire vectors, complete
byte reconstruction, additional-header budget boundaries, metadata conflicts,
empty/one-part/multipart limits, version and TLV-negotiation rejection, and
ownership tests. Session tests must cover client/server sends, shared-reference
capacity, cancellation, partial writes, response errors and unscheduled parts.
Reuse existing receiver tests and add binary round-trip coverage with independent
wire evidence; shared-Codec interoperability alone is insufficient.

Add compiling planning/sending examples and benchmarks for preparation,
materialization and sending, including allocation and ownership-copy behavior.
Do not use arbitrary private payloads or consumer business code as fixtures.

## Implementation sequence and release gates

F1/F2 and the identifier/DCS tables are implemented/finalized locally. API,
independent fixtures, examples, tests and benchmarks are recorded in the linked
validation records. The [overall local review](../v1.2.0-review.md) found no blocking code issues;
release notes are finalized in the [publication checkpoint](../v1.2.0-release.md);
submitted-revision CI and publication gates remain pending. Historical sequencing follows; this is not a release-readiness claim.

1. **API and contract review:** inventory semantic checks, fix stable identifiers,
   settle byte input/policy/result contracts and the version/DCS support table.
2. **Semantic diagnostics:** implement the cause type and validator integration;
   promote independent failure samples to regressions, add comments and examples.
3. **Binary planning and Session integration:** implement the planner first,
   then integrate with the existing send path; retain text regressions and
   explicit reference ownership, limits and outcome semantics.
4. **Verification and documentation:** run build, vet, race and applicable fuzz
   and allocation benchmarks; update the API snapshot, support matrix, examples
   and README with actual implemented capabilities and measured results.
5. **Release review:** verify the final submitted revision's CI, then follow
   the existing tag/publication gates. Do not waive failures or rerun unexplained
   failures into success. Preserve Go 1.26's execution-budget fuzz policy unless
   a separately verified toolchain change justifies adjusting it.

## Scope boundaries

The discussed missing-bind-version compatibility option is **not included** in
these two approved planning items. v1.1.0's default negotiation policy remains.
Any future peer exception requires its own explicit scope and evidence.

Applications retain connection/reconnection management, sending-domain reference
sharing and capacity choices, REST binary representation (for example base64),
per-segment ID association, receipt-source conflict policy and storage. No
persistence, delivery engine, routing, HTTP callbacks, automatic reconnection or
business retries enter the public library. Reference repositories remain read-only.
