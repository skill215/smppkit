# v1.2.0 feature design: diagnostics and binary messaging

Updated: 2026-11-06 (Asia/Shanghai). This document refines the two enhancements in
the [roadmap](roadmap/v1.2.0.md). F1 and F2 are implemented locally and unreleased.
Release documentation is finalized in the [publication checkpoint](v1.2.0-release.md);
publication still requires candidate CI and separate authorization.
The [semantic identifier catalog](semantic-diagnostics.md) and
[binary DCS table](binary-dcs.md) are finalized. F2 API names/signatures are fixed in the
[binary contract](binary-messaging.md). See the [F1 validation record](v1.2.0-f1-validation.md)
and [F2 validation record](v1.2.0-f2-validation.md).

## Release objective and priorities

Make protocol failures inspectable without parsing prose, and make bounded
binary multipart sending as accessible as text sending. Preserve Go 1.26,
concrete PDUs, versioned Codec and shared Session. The release is a compatible
API addition; valid existing text and protocol behavior must remain intact.

| Priority | Feature or deliverable | Release status |
| --- | --- | --- |
| P0 / F1 | Stable semantic field and rule identifiers | Core feature |
| P0 / F2 | Binary preparation and client/server sending with per-segment outcomes | Core feature |
| P1 | Compiling examples for F1/F2, independent fixtures, allocation benchmarks and updated contracts | Required evidence and usability work for the core features |
| Candidate | Application-owned reconnect and pacing examples | Useful future work; not added to this release scope |
| Deferred | Missing-bind-version compatibility, additional alphabets/packed GSM, multipart pipelining, broadcast and a dedicated CLI | Separate decisions; not v1.2.0 requirements |

The [comparison and lessons](go-smpp-comparison.md) inform API usability; they do
not require matching another library's complete feature list. No persistence,
delivery engine, reconnect manager, automatic replay or consumer-specific logger
interface is introduced.

## F1: stable semantic diagnostics

### Public contract (unreleased)

The local implementation introduces `codec.SemanticError`, exposing stable
`Field` and `Rule` identities. Illustrative caller code:

```go
var diagnostic *codec.SemanticError
if errors.As(err, &diagnostic) {
    // Branch on documented identifiers, not diagnostic.Error().
    recordRule(diagnostic.Field, diagnostic.Rule)
}
```

Field identity uses protocol terminology, for example `source_addr_ton` or
`data_coding`. Rule identity describes the failed constraint independently of
the field or offending value. Categories include invalid assignments,
reserved bits, unsupported version/command, required-empty fields and conflicting
metadata. The actual identifier catalog must describe existing checks rather
than inventing validations or guessing identity from old error strings.

Published identifiers retain their meaning within v1; future identifiers may
be added and callers need a fallback. Human-readable error wording remains
non-contractual. Do not promise which error wins when multiple independent
constraints fail unless an existing documented contract already requires it.

The diagnostic identifies repeated items with Index/HasIndex, and TLVs with
Tag/HasTag, without including values. Index is zero-based in the complete source
slice, not a per-tag occurrence count. Nested destination paths and exclusions
are fixed in the catalog. Historical FieldError causes/classifications survive;
no recursive error tree or aggregate-validation API is added.

### Integration and compatibility

- Apply identifiers to existing built-in semantic checks on encoding, decoding
  and applicable contextual validation APIs. Inventory header, mandatory body,
  response, standard TLV and data_sm direction/transaction checks separately.
- Preserve existing errors.Is causes and errors.As behavior. In particular,
  structural FieldError remains structural; SemanticError must not be a
  wire.Error alias. DecodeError remains the outer decode context and preserves
  its existing Kind, including DecodeTLV for optional-section failures.
- Unsupported operations with no meaningful field need not acquire a fabricated
  Field identifier. Explicitly record such exclusions in the coverage inventory.
- A custom validator's arbitrary error remains its cause. Built-in context may
  identify the callback location, but must not pretend to know the callback's
  semantic rule or parse its error text.
- Built-in diagnostic formatting contains identifiers and safe numeric context,
  not credentials, addresses, message bytes or TLV contents. Arbitrary extension
  causes retain the existing caveat about logging their text.
- Do not automatically map a rule to an SMPP status, NACK, retry or disconnect.
  Those decisions depend on command, transport state and application policy.

Keep this integration inside the existing validation paths. Helpers can construct
the new cause at a check site; avoid a second validation pass or rule engine.
Existing combined checks may need local refactoring to identify the failing
field, without changing the set of accepted inputs.

### Acceptance

Publish a check-to-identifier inventory and verify representative range,
version/direction, dependency, repeated-destination and TLV cases using independent
wire inputs. Compare equivalent typed and decoded failures where applicable.
Test old sentinels/classifications, absence of sensitive values and unchanged
valid-input behavior. Benchmark successful validation and failure construction;
report B/op and allocs/op without claiming they count copies.

## F2: binary preparation and sending

### Public surface (unreleased)

Use a distinct byte-oriented input and policy without overloading text.Encoding
or interpreting strings as binary. Implemented entry points:

```go
// package message
func PrepareBytes(version pdu.Version, msg Binary, policy BinaryPolicy) (*Plan, error)

// package smpp
type BinaryMessage = message.Binary
func (s *Session) SendBinary(ctx context.Context, msg BinaryMessage,
    policy message.BinaryPolicy, references ...*message.References) (SendResult, error)
```

Binary contains the existing logical addressing/service/receipt-request metadata,
raw Data bytes, an explicit DataCoding value and caller optional fields.
BinaryPolicy contains mode, radio-octet budget, additional UDH and resource
limits. It has no Encoding or Fallback members. This avoids meaningless
combinations such as requesting text fallback while supplying raw bytes.

Do not embed or alter exported Text/Policy structs merely to share fields.
Internal helpers can share metadata validation, budgeting and materialization.
Binary carries Source, Destination, Data, DataCoding, ServiceType,
RegisteredDelivery and Optional. BinaryPolicy carries Mode, PayloadOctets,
AdditionalUDH, MaxInputBytes, MaxOutputBytes and MaxSegments. Existing text callers
require no migration. MaxOutputBytes was chosen instead of MaxEncodedBytes
because binary input is not encoded and repeated metadata must be bounded.

### Bytes, DCS and ownership

- Preserve all bytes, including NUL and invalid UTF-8. No charset conversion,
  fallback, sniffing or string intermediary is performed.
- The finalized binary DCS whitelist is 0x04 for 3.3 and 0x02/0x04 for 3.4/5.0.
  See the sourced binary DCS table for excluded groups and the distinction
  between high-level policy and raw Codec acceptance. Zero is not a default.
- Do not promise safe splitting of arbitrary pre-encoded text. Existing text
  Encoding already returns boundaries and unit width; no new Splitter interface
  is needed for raw octet segmentation.
- Preparation checks limits before large copies and snapshots caller bytes,
  optional values and additional UDH. Callers must not mutate inputs concurrently
  with preparation/sending. Plan methods return owned outputs as they do today.
- Reuse immutable Plan. Use the diagnostic Encoding label `binary` for byte
  plans and SendResult; it denotes no conversion, while Plan.DataCoding retains
  the numeric mapping. This convention is part of the F2 contract.

### Segmentation and Session behavior

Use the existing UDH8/UDH16/SAR/Payload modes where the selected version and
negotiated peer policy permit them. Payload remains one request, with further
segmentation owned by the peer. Additional application-port UDH consumes the
same radio budget as concatenation metadata. Reject conflicting generated and
caller metadata and retain existing national-language declaration protection.

Defaults follow text preparation: 140 radio octets, 64 KiB input and
at most 255 segments. MaxOutputBytes defaults to 256 KiB of accounted
materialized storage:
256 bytes per part plus repeated address/service lengths, payload/UDH bytes,
and 32 bytes plus value length per caller/generated TLV. Input/output limits
are capped at 16 MiB. These checks precede input/TLV copies; this is accounting,
not an exact heap/RSS limit. See the binary contract for examples and exclusions.
Empty bytes produce one empty message, matching Plan.Count's existing contract.
There is no truncation or silent policy fallback. Version/command short_message
and TLV size limits still apply even when a policy allows a larger logical input.

Client sends use submit_sm; server sends use deliver_sm. Preserve existing
high-level 3.3 submission restrictions and the absolute prohibition on 3.3 TLVs.
Do not use this feature to weaken bind negotiation or add implicit peer dialects.

A private shared sendPlan helper lets SendText and SendBinary
use the same preflight, reference leasing, role/TLV admission and Request path.
Both must validate every segment before consuming a lease or writing the first
segment. No public SendPlan API is required for this release.

Keep sequential per-message sends and the existing SendResult/SegmentResult
contract: all planned parts remain visible; failures stop later scheduling;
unattempted parts stay distinguishable from failed attempts. Timeouts and partial
writes retain uncertainty. Submission acceptance does not mean delivery and
does not release a reference lease early. Applications can continue sharing
References across Sessions. No automatic business retry is added.

### Reception and acceptance

Use the existing bounded Receiver for raw reassembly; no parallel binary receiver
or new ACK mode is needed. The example must show how to consume reassembled bytes
without assuming that they are decodable text. Keep ACK-on-memory-admission and
application-controlled response choices explicit.

Tests cover independent UDH8/UDH16/SAR/Payload byte samples, reconstruction,
empty/exact-fit/oversized input, ports, metadata conflicts, ownership and
version/negotiation rejection. Reuse Session tests and extend only real gaps:
client/server sending, capacity, cancellation, partial results and shared leases.
Retain existing text regressions when extracting shared internals.

Provide compiling binary preparation and client/server usage examples, plus
benchmarks for preparation, materialization and sending at representative sizes.
Explain allocation/copy boundaries and exclude setup from the measurements.
Do not infer zero-copy or network TPS from local benchmarks.

## Implementation entry gates and sequence

1. Freeze the semantic identifier/location inventory and the version/DCS table.
   Review draft types for meaningful zero values, ownership, error causes and
   compatibility with existing public structs/interfaces.
2. Implement F1 with focused regressions and independent byte cases. Update the
   diagnostic documentation before using the identifiers in examples.
3. Implement byte preparation, then reuse the Session send path for F2. Verify
   the unchanged text path alongside new binary behavior.
4. Complete compiling examples, support/API snapshots, build, vet, race,
   applicable fuzz and allocation benchmarks. Record actual execution evidence.
5. Review the final release scope and CI before publication. This design work
   itself authorizes neither a release nor new compatibility exceptions.

The identifier/DCS tables and F2 API are now fixed; release review does not
authorize adding features.
No external SMSC access is a release prerequisite. If API review discovers an
incompatible change or a substantially broader protocol requirement, resolve
that scope explicitly before implementing it.
