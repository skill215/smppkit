# RV25: revalidate release refs after CI

2026-10-29 (Asia/Shanghai). **Corrected and locally reviewed; candidate
commit/push is authorized, tagging and publication are not.** Go remains 1.26. No library code,
public API, protocol scope or runtime dependency changes.

## Defect and correction

The release workflow checked candidate/main identity before waiting for main
and tag CI. It then published by tag name without checking the refs again.
If main advanced during the wait, the advertised main/tag identity no longer
held. If the tag moved, the release could name a different commit from the one
whose CI links appeared in its notes. `gh release create --verify-tag` checks
existence, not equality with the tested commit.

The workflow now calls [.github/scripts/release.sh](../.github/scripts/release.sh).
Its original version/notes checks, initial main check, CI polling, unsuccessful
CI rejection and publication arguments are preserved. After both CI runs pass,
it reads remote main again and resolves the remote tag to a commit. Both must
equal the candidate SHA immediately before `gh release create`; otherwise the
script exits unsuccessfully without publishing.

Lightweight tags resolve directly. Annotated tags are peeled through the Git
database API, including nested tags, with at most 16 tag-object dereferences.
Missing refs, API errors, malformed objects, non-commit targets and excessive
chains fail closed. The resolver explicitly propagates command failures out of
its command substitution; it does not depend on Bash inheriting `errexit` there.

This closes the unchecked CI-wait interval. Ref reads and release creation are
separate GitHub operations, not an atomic transaction. A concurrent ref change
after the final reads remains possible; this correction does not claim to lock
remote refs or replace the existing rule against moving release tags.

## Regression evidence

[The formal tests](../.github/scripts/test_release.py) execute the actual release
script with local `gh`, `git` and `sleep` stubs and real JSON parsing through jq.
No stub delegates to GitHub. They need Python 3's standard library, Bash and jq,
and fail if a prerequisite is missing. They are part of both existing Go CI
matrix jobs; all Go checks and 14 fuzz targets remain unchanged.

```sh
bash -n .github/scripts/release.sh
python3 .github/scripts/test_release.py
```

Four test groups cover 14 scenarios:

| Scenario | Required result |
| --- | --- |
| Unchanged lightweight, annotated and nested annotated tags | Publish stub reached with the verified SHA and main/tag CI links |
| Main, lightweight tag or annotated tag moved during CI | Nonzero exit; publish stub never called |
| Final main API failure, missing tag or tag-object API failure | Nonzero exit; publish stub never called |
| Malformed tag SHA, non-commit target or cyclic tag chain | Nonzero exit; bounded resolution; publish stub never called |
| Failed main CI or failed tag CI | Nonzero exit; publish stub never called |

[Baseline reproduction](validation/v1.1.0-rv25-baseline.txt) runs the same
three ref-change scenarios against the original workflow script from
`fb52051997c8b7e50e644e365f7240419ec85f44`: all three incorrectly reach the
publication stub. [Correction checks](validation/v1.1.0-rv25-checks.txt) record
the successful formal regressions, syntax/configuration review and unchanged
source boundary.

The subsequent local recheck found no new blocker and verified that these
script/workflow hashes still matched the successful regression record. Two
additional isolated probes confirmed the dereference boundary: a 16-tag chain
resolves successfully, while a 17-tag chain stops without publication after
16 lookups. No real GitHub publication was attempted.

The 108 Go/module entries still match the S5 correction manifest. Existing
build/vet/race/fuzz evidence on `fb52051` is reused for that unchanged code;
those checks are not claimed as new runs for this script-only correction.
The corrected workflow still needs CI on its eventual submitted revision.
Tagging and publication continue to require explicit authorization.
