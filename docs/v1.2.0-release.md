# v1.2.0 publication checkpoint

Prepared 2026-11-06 (Asia/Shanghai). **Release candidate documentation finalized;
not tagged or published.** No publication date is assigned.

The maintainer authorized release preparation, candidate commit/push and CI
verification. Creating a v1.2.0 tag or formal GitHub Release is explicitly outside
this authorization. That remains a separate step after successful candidate CI.

## Candidate scope

Exactly two features: F1 stable semantic diagnostics and F2 bounded binary
preparation/sending. The [overall review](v1.2.0-review.md) found no actionable
blocking code issue. Production sources are unchanged by this preparation stage;
it packages the previously reviewed implementation, tests, examples, benchmarks,
public contracts and evidence alongside the release documentation.

The [release notes](releases/v1.2.0.md), [README](../README.md),
[changelog](../CHANGELOG.md), [roadmap](roadmap/v1.2.0.md),
[support matrix](support.md) and [API snapshot](api-v1.2.0.txt) describe the
candidate without claiming publication. The existing comparison/design inputs
are included as public documentation. Historical F1/F2/review records retain
their stage-specific dates and uncommitted status; this checkpoint records the
subsequent preparation stage.

Go remains `1.26.0`, with the existing Go 1.27.x CI job only providing additional
compiler coverage. No new runtime dependencies, architecture changes, persistence,
delivery system or external interconnection requirement were introduced.
Apache-2.0 and the existing AI disclosure remain unchanged. /doc/ stays ignored.

## Validation and identity

[Candidate checks](validation/v1.2.0-candidate-checks.txt) record packaging,
formatting, local build/vet/race and publication-gate stub checks. The earlier
[F1](v1.2.0-f1-validation.md), [F2](v1.2.0-f2-validation.md) and
[review](v1.2.0-review.md) evidence describes its actual executed scope; native
fuzz/benchmark runs are not relabeled as new preparation runs. New console
artifacts had trailing whitespace/extra EOF blank lines normalized during staged
packaging checks; result lines, execution counts and measurements are unchanged.

[Candidate source manifest](validation/v1.2.0-candidate-manifest.txt) fingerprints
the Go sources, module, CI and release-gate scripts selected for submission.
Actual commit/Actions identities become available only after commit/push. The
submission report must identify the exact SHA, remote main and its Go workflow
run, including both matrix jobs. This preparation checkpoint does not predeclare
a remote CI result or claim a published release.

The CI matrix runs build, vet, full race, publication-gate stub tests and fifteen
native fuzz targets. Keep the Go 1.26 million-execution budget, Go 1.27 time
budget, failure propagation and failing-corpus retention. Investigate a failure;
do not bypass tests or rerun an unexplained failure to obtain success.

## Publication gates still required

1. Verify the candidate's first push CI against its exact SHA and remote main.
2. Obtain explicit authorization to tag and publish v1.2.0. Candidate push
   authorization does not permit tagging or formal publication.
3. Reconcile notes/version status with that action; do not invent a publication
   date or overwrite an existing tag.
4. Push the authorized tag only at the verified main revision. The Release
   workflow checks main/tag identity, requires successful main and tag CI on that
   commit, rechecks both remote refs immediately before publication, then creates
   the Release using these notes. Any mismatch or failed lookup blocks it.

No tag or Release is created by this checkpoint. Candidate submission completion
and its CI links are reported separately after the real remote checks finish.
