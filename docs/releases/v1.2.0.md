# smppkit v1.2.0

Stable semantic diagnostics and bounded binary multipart sending for Go SMPP
clients, servers and standalone protocol tools.

**Release candidate; not yet tagged or published.** Notes finalized 2026-11-06
(Asia/Shanghai). Publication requires successful candidate/tag CI and separate
maintainer authorization. No publication date is assigned. See the
[publication checkpoint](https://github.com/skill215/smppkit/blob/main/docs/v1.2.0-release.md)
for the submission and release gates.

Requires **Go 1.26 or newer** (`go 1.26.0` in go.mod). The module remains
`github.com/skill215/smppkit`, root package `smpp`, under Apache-2.0 with no
third-party runtime module dependencies.

## Stable semantic diagnostics

`codec.SemanticError` exposes stable `Field` and `Rule` identifiers, with
`Index`/`HasIndex` for repeated items and `Tag`/`HasTag` for optional parameters.
Sixteen `SemanticRule` constants identify existing checks without parsing error
prose. Inspect them with `errors.As` or Go 1.26 `errors.AsType`.

Existing validation sites gain diagnostics; valid protocol acceptance is not
narrowed. Historical sentinels, FieldError causes and DecodeError classifications
remain accessible. Four historical semantic decode checks still classify as
DecodeMandatory and retain FieldError rather than acquiring ErrValidation.
Customer TLV validator causes, previously discarded, are now retained alongside
ErrValidation. The outer summaries omit callback text and input values; arbitrary
unwrapped causes can still contain application data.

Identifiers are open-ended: callers must tolerate future additions. Structural
framing/truncation/C-octet errors, Session state and message-preparation errors
keep their existing contracts. There is no automatic status, retry or disconnect
mapping. See the [field/rule catalog](https://github.com/skill215/smppkit/blob/main/docs/semantic-diagnostics.md).

## Binary preparation and sending

New `message.Binary`, `BinaryPolicy` and `PrepareBytes` prepare raw octets into the
existing immutable Plan. `smpp.BinaryMessage` and `Session.SendBinary` send through
the same sequential preflight, reference leasing and Request path as SendText.
NUL and invalid UTF-8 are preserved; no charset conversion, sniffing or fallback
occurs. Plans and send results use the encoding label `binary`.

| Profile | Explicit binary DCS | High-level support |
| --- | --- | --- |
| SMPP 3.3 | `0x04` | Header-free, TLV-free single-part message |
| SMPP 3.4 / 5.0 | `0x02`, `0x04` | UDH8, UDH16, SAR and message_payload, subject to command and negotiated TLV rules |

Zero is not a default DCS. This whitelist does not restrict the low-level Codec.
BinaryPolicy defaults to UDH16, 140 radio octets, 64 KiB input, 255 segments and
256 KiB of accounted materialized output. Output accounting includes repeated
metadata and generated headers/TLVs; it is not an exact heap limit. Payload is
one SMPP request with radio segmentation owned by the peer. Its 65535-byte TLV
maximum can exceed the default Codec total-frame cap and therefore still fail
preflight.

All parts are preflighted before leasing a reference or writing the first part.
Applications can share References across text/binary sends and connections.
Existing SegmentResult outcomes and opaque per-part IDs remain available on
partial failure; later parts remain NotAttempted. Success does not release a
reference early or prove final delivery. No automatic retry was added.

Receive through the existing bounded Receiver and consume Message.Payload as
bytes, without selecting a text decoder for DCS 2/4. ACK-on-memory-admission and
application-controlled responses are unchanged. See the
[binary contract](https://github.com/skill215/smppkit/blob/main/docs/binary-messaging.md)
and [DCS policy](https://github.com/skill215/smppkit/blob/main/docs/binary-dcs.md).

## Compatibility and scope

The six public packages, concrete PDUs, versioned Codec and shared Session remain.
Existing exported struct fields and required interface methods are unchanged.
Text encoders, fallback and character boundaries are unchanged. New types and
methods are additive under the v1 compatibility policy; error text and direct
outer-type assertions are not stable contracts.

No persistence, delivery engine, routing, reconnect manager, automatic replay,
missing-bind-version exception, broadcast, packed GSM or national-language codec
is added. SMPP 3.3 remains TLV-free and has no high-level multipart support.
External SMSC interoperability is not newly claimed.

## Examples and validation

- New runnable diagnostic and binary preparation examples.
- Client/Server demos accept raw hexadecimal input and can echo binary payloads
  through deliver_sm. Echo is a new message, not a receipt or handset verdict.
- Independent complete protocol frames, DCS enumeration, boundary/ownership/
  concurrency tests and reused transport-failure/reference regressions.
- Nine F1 diagnostic and fourteen F2 binary benchmark cases, with B/op and
  allocs/op. Copy boundaries and setup costs are documented; no zero-copy or
  network-TPS claim is made.

Local Go 1.26.10 build, vet and full race checks passed during implementation and
[overall review](https://github.com/skill215/smppkit/blob/main/docs/v1.2.0-review.md).
F1 ran eight native Codec fuzz targets at one million executions each; F2 ran five
message targets at the same budget. Review additionally compared 300000 mutated
frames against v1.1.0 and checked 28622 accepted binary accounting/reassembly
combinations. These are finite local checks, not conformance certification.

The CI matrix retains Go 1.26.x and additional Go 1.27.x coverage, now with fifteen
fuzz targets including FuzzPrepareBytes. Go 1.26 uses execution budgets to avoid
its known timed-shutdown issue; failures are not filtered or retried into success.
Candidate CI must be verified against the exact pushed SHA. Historical/local
results do not certify a later commit or tag; the release workflow checks main
and tag identity and appends verified commit/CI links when publishing.
