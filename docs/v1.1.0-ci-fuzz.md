# Go 1.26 fuzz shutdown diagnosis and CI correction

2026-10-29, Asia/Shanghai. Go remains 1.26; this changes CI and documentation,
not public APIs, library code, test assertions, or the release scope.

## Original failure

Candidate `e1083a02245f2d09a0aad48b7f3076437f82d0be` failed
[Go workflow 40827967811, attempt 1](https://github.com/skill215/smppkit/actions/runs/40827967811).
The Go 1.26.10 job passed formatting, build, vet, full race tests and its first
four fuzz targets. `FuzzStandardTLVSection` then exited after 5.062 seconds and
251,408 executions with `context deadline exceeded`. The Go 1.27.3 job passed
all 14 fuzz commands but was cancelled by matrix fail-fast; it is not a passed
job. Neither job was rerun to change that result.

The original workflow did not retain failing corpus files. Absence of a
`Failing input written to` line cannot prove that no input triggered a defect:
the upstream report also describes this shutdown error obscuring a crash report.
We cannot recover that original runner's corpus or retrospectively certify it.

## Mechanism and controlled reproduction

Go 1.26.10 still contains the cancellation race reported in
[golang/go#75804](https://github.com/golang/go/issues/75804).
`internal/fuzz.CoordinateFuzzing` creates a timeout parent context and a worker
child context. On parent completion it calls `stop(ctx.Err())`, but suppresses
the error only when it equals `fuzzCtx.Err()`. Context cancellation records the
parent error and closes its Done channel before propagating cancellation to
children. The coordinator can therefore observe `DeadlineExceeded` for the
parent and nil for the child, incorrectly reporting normal budget expiry as a
test failure.

The installed source hashes match the previously diagnosed Go 1.26 code in the
[R3 record](r3-validation.md). Ten bounded runs with diagnostic logging alone
all passed this time; these are diagnostic attempts, not a replacement for the
failed remote check. A separate scheduling experiment widened the existing
parent/child cancellation gap by 10 ms using temporary `go -overlay` source
copies. It reproduced the exact state and error:

```text
incoming=context deadline exceeded parent=context deadline exceeded child=<nil>
--- FAIL: FuzzStandardTLVSection (5.03s)
    context deadline exceeded
```

With the same scheduling injection, `-fuzztime=10000x` passed. This establishes
the mechanism under controlled scheduling; it is not an internal trace captured
from the original GitHub runner. The installed toolchain was never edited.
[Source hashes, diagnostic diffs, commands and output excerpts](validation/v1.1.0-ci-fuzz-diagnostic.txt)
make this experiment reproducible. Production checks use unmodified Go and no
overlay or diagnostic environment setting.

The [Go 1.26 backport issue](https://github.com/golang/go/issues/82362) is open
and targeted at Go 1.26.11 as checked on this date. A later released patch can be
evaluated separately; this correction does not upgrade the minimum Go version
or depend on an unreleased toolchain.

## CI policy

The [Go workflow](../.github/workflows/ci.yml) keeps every existing target,
seed, assertion and the two-worker setting:

- Go 1.26: native `-fuzztime=1000000x` for each of all 14 targets.
- Go 1.27: the existing `-fuzztime=5s` for each of all 14 targets.
- Both compilers: formatting, build, vet and full race tests remain required.
- No retries, error-text filtering, `continue-on-error`, target removal or
  patched toolchain. Any nonzero test exit still fails its job.
- Matrix `fail-fast: false` lets the other compiler complete its evidence when
  one fails. It does not turn either failure into a success.
- Each fuzz command has a ten-minute Actions step cap, and the job has a
  45-minute cap. The additional Go `-timeout=9m` only bounds the pre-fuzz test
  phase: Go disables that alarm before active fuzzing. The Actions cap enforces
  the active campaign's wall-clock limit. Reaching a cap fails; it is not a
  successful stopping condition. The local runner similarly uses an external
  ten-minute subprocess limit per command.
- On failure or cancellation, upload any `**/testdata/fuzz/**` corpus for 30
  days. If a runner is terminated before upload or no corpus is written, the
  artifact may be absent; the test result remains a failure.

The [documented execution budget](https://pkg.go.dev/cmd/go#hdr-Testing_flags)
sets the fuzz coordinator's execution limit. Normal completion calls
`stop(nil)` without creating its time-budget parent context, avoiding the faulty
expiry path. This is not `-count`, which repeats test runs. One million exceeds
every per-target execution count observed in the failed candidate's five-second
matrix (maximum 416,105); it does not imply identical inputs or a proof of equal
coverage. Count budgets can take longer on slow targets or runners.

The [publication workflow](../.github/workflows/release.yml) now allows up to
50 minutes to observe each required CI run, within a 60-minute release job cap,
instead of its old ten-minute poll window. Main/tag identity and successful CI
remain mandatory. This adjusts status polling, does not rerun tests, and does
not authorize a tag or release.

## Validation

The [negative control](validation/v1.1.0-ci-fuzz-negative-control.txt) uses a
temporary module whose fuzz target deliberately fails on a mutated boolean.
Unmodified Go 1.26.10 with the new million-execution budget exited nonzero with
the assertion and wrote a reproducible corpus file. This checks that real
target failures remain visible; it is not a failing smppkit test.

[Fresh Go 1.26.10 build, vet and full race checks](validation/v1.1.0-ci-fix-checks.txt)
passed. Workflow YAML parsing, shell syntax, the unchanged target inventory and
formatting are checked separately; no smppkit Go source or module file changed.

[Local execution-budget output](validation/v1.1.0-ci-fuzz-counts.txt) records
all 14 original targets passing at 1,000,000 executions each (14 million total),
using unmodified Go 1.26.10. Each command and exit status are retained. The
campaign was configured to stop on the first error and performed no retries. Local validation and
new-commit remote CI must be assessed separately. No new remote success is
claimed by this pre-commit record; the pushed SHA and its workflow result must
be checked together before publication can proceed.
